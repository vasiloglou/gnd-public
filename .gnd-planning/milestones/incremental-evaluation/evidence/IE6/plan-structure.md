# IE6 amendment review — structure and feasibility

Verdict: **accept for the delegated plan/spec gate, with implementation hardening below**. I found no concrete blocking contradiction or missing architectural prerequisite in the proposed scope. This is an independent read-only review of the IE6 amendment and draft spec, not a review of implemented IE6 bytes or a prediction of a speedup.

I also read AGENTS.md, the retained Astra summary, incremental_state.py, the actual correspondence/extension reuse setup, the existing prepared-policy and private-clone/bounds controls, and pertinent layer/source-successor controls.

## Checked architectural claims

- The proposed primary home is appropriate. incremental_state already owns normalization, policy authority, signature comparison, bounded measurement, private cloning, retained-generation charging and publication. Adding private immutable accounting metadata there avoids a second dependency or family-dispatch policy and needs no new runtime layer. Its existing map assignment is checking, with zero allowances declared.
- The proposed hotspot is present in source: prepare_policy measures a normalized key once; reuse then hashes the whole signature on every lookup and measures the full signature twice on misses, including after cloning. A verified normalized-policy record can avoid repeatedly visiting invariant descendants while preserving exact equality and charging their retained footprint conservatively.
- The spec explicitly retains live function-code and mutable-configuration checks at each reuse boundary. The current _PreparedPolicy authority is transaction-local, so its preparation is not permission to memoize new mutable configuration or registry membership across boundaries. The optional correspondence/extension work is properly conditional; neither is required to make the state-level optimization feasible.
- The unchanged _measure return contract and private-clone measurement preserve existing direct consumers. The existing test_accounting_measures_the_private_clone independently compares stored entry size against the actual retained key/signature/value/branches, and the selection includes it. Existing proxy backing-storage and changed-binding tests cover two particularly easy undercount errors.
- The affected-consumer selection is proportionate for changes within the stated homes: direct state/prepared-policy/extensions/session/observation, receipt/admission/correspondence, API signatures, layer/query/source controls, integrated parity and an outside-checkout wheel smoke. No broad/native/provider lane is necessary merely to accept this bounded plan. Actual changed definitions must determine any extra authenticated source successors; existing passing pins cannot be treated as evidence for newly changed bodies.
- The new phase leaves historical close evidence intact and adds renewed close. Its deterministic reduction gate and honest same-host timing protocol do not silently convert IE5's informational timing criterion into an invented elapsed target. A smaller repeated-work count alone must not be described as a successful speed improvement.

## Hardening and completeness to enforce during implementation

1. Cached policy metadata must be internal and verifiably attached to the normalized immutable tree, rather than accepted from an arbitrary caller-provided wrapper or trusted by a mutable public size/hash field. Keep original code/identity guards and exact structural equality, including equality under hash collisions. A precomputed hash is a lookup aid, never an equality proof.
2. Account for the wrapper and metadata themselves and conservatively charge the entire normalized tree whenever retained in an entry, even if entries share it. A measurement shortcut must also carry sufficient logical node/depth information to preserve enclosing measurement limits: a deeply nested or too-large key must not become admissible just because descendants are skipped. Test preparation bounds and enclosing-entry bounds separately. The draft already requires these properties; this is implementation guidance, not a new acceptance condition.
3. Fast-path only exact builtin types. Preserve dataclass handling, unknown/subclass refusal, nonfinite rejection, cycle handling, proxy backing storage and actual private-clone measurement. Keep evaluator execution outside optional-key setup catches so a failure is never retried into a different outcome.
4. Count actual traversals at their defining lookup owners. Add discriminators for preparation once versus repeated miss/hit accounting, and for changed policy content. A counter attached only to the new fast branch could pass while a hidden full-policy walk remained elsewhere. The proposed RED-on-d0ffd9a protocol plus existing integrated work accounting is the right defense.
5. If optional setup optimization is attempted, do not hoist namespaces, registry values, mutable defaults/closures, relation validation or ModelIndex checks merely once per evaluation. Those values currently participate in live eligibility. Restrict initial implementation to the primary state optimization if preserving those boundaries makes the optional work broad or weakly measured; the spec expressly permits this.

These are concrete review checkpoints already supported by the spec, not plan blockers. The estimate is plausible for the primary state change; a materially larger optional setup refactor should be documented and rechecked against the actual affected closure rather than justified by the rough line estimate.
