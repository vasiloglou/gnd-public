# DB2 · Read-only DuckDB relation bindings

Address #327 by adding api.check_duckdb(model, database, *, bindings, max_examples=20, timeout_seconds=30). The caller supplies a standalone validated model path, an existing local file, and a mapping with version 1 and a facts dictionary keyed by asserted fact ID. Each entry names a base table in the current database's main schema and maps each role to an exact column name. The opt-in instances dictionary maps an object type to an explicit roster table and column. A missing or incomplete required binding must be distinguishable from an empty covered relation. An empty roster is explicit. For mandatory rules combine all relevant, covered role projections with that roster in the universe; refuse unimplemented subtyping or entity identity. No cursor, caller SQL, external views or hosted service.

Return a versioned database-check report with exit code, per-constraint pass/fail/warning/vacuous/unchecked, exact violation count, bounded typed witnesses, truncation, and identities of model bytes, database snapshot and normalized bindings. Apply the ordinary modality and outcome order. In customer mode or restricted roles omit witness values. The supported scalar fragment starts with String, Boolean and signed Integer; reject incompatible SQL types. Reject NULL explicitly before constraint evaluation. Preserve physical duplicate facts in the uniqueness check, including a full-key duplicate. Native GND on the basics_fail fixture returns two identical offending_facts for student_has_nickname. Inclusion and mandatory use membership and deduplicate the missing keys. This supersedes the revision-2 assumption of set semantics for uniqueness. Support internal uniqueness, subset of matching single-fact projections including compound keys, and fact-level mandatory participation; report unsupported constraints and model features explicitly. Implement primitive and role lookup using ModelIndex. A dedicated module owns optional backend admission and query execution; normal Python and CLI check behavior stays as before.

Use one read-only transaction, no external access or extension autoload, only catalog-verified base tables, properly quoted identifiers and parameterized catalog lookups. Limit the engine's memory and threads and support a bounded statement deadline. Format deterministic witnesses using typed role values; return 0 to 100 records with a truncation bit, independent of total count. Measure transaction and projection identity and check that fixture data and file bytes remain unchanged. Exercise passing and failing examples for all three families, missing mapping/table, NULL, type mismatch, physical duplicates, stable witnesses at zero and one, an unusual quoted identifier, a refused write through the actual opener and privacy projection. DB3 owns native differential replay and backend agreement at the advertised boundaries.
